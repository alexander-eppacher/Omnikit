# 0016 – Server und Agent

**Datum:** 02.11.2026

**Entscheidung:**
- **Server:** ASP.NET Core (.NET 10). Die Verwaltungsoberfläche besteht aus **Razor Pages** (HTML entsteht auf dem Server) statt der ursprünglich geplanten React-App: npm/Vite wird in der Entwicklungsumgebung blockiert (siehe 0012), und so gibt es keine JavaScript-Abhängigkeiten, die gepflegt werden müssen. Schutz gegen Formular-Fälschung (Antiforgery) ist eingebaut.
- **Datenbank:** *(seit 11.11.2026 nur noch SQLite mit Migrationen, siehe 0017)* EF Core mit PostgreSQL (`Npgsql.EntityFrameworkCore.PostgreSQL`, PostgreSQL-Lizenz – BSD-ähnlich, kommerziell nutzbar) im Betrieb, SQLite (`Microsoft.EntityFrameworkCore.Sqlite`, MIT) für Tests und lokale Entwicklung. Tabellen werden beim ersten Start angelegt (`EnsureCreated`); Migrationen kommen, sobald sich das Schema nach einer Veröffentlichung ändert.
- **Agent:** Windows-Dienst (`Microsoft.Extensions.Hosting.WindowsServices`, MIT) als LocalSystem. Pull-Prinzip: Der Agent fragt den Server, der Server baut nie eine Verbindung zum PC auf; am PC ist kein Port offen.
- **Anmeldung des Agents:** einmaliger Registrierungscode (24 h gültig, nur einmal nutzbar) → gerätespezifischer Token. Server speichert Codes und Tokens nur als SHA-256-Hash (zufällige 256-Bit-Werte, daher reicht ein schneller Hash).
- **Aufgaben:** feste Liste – „Programm installieren“ und „Programm aktualisieren“ mit einer geprüften winget-Paket-ID. Ablauf: angelegt → **freigegeben (nur Admin)** → vom Agent abgeholt → Ergebnis. Kein beliebiger Code vom Server. Der Agent holt Aufgaben **einzeln** ab (Ergebnis melden, dann die nächste), damit die Zeitgrenze erst mit dem Start der Aufgabe beginnt. Kommt 45 Minuten lang kein Ergebnis (winget bricht nach 30 Minuten ab), gilt die Aufgabe als fehlgeschlagen; das prüft der Server beim Abruf und alle 5 Minuten für alle Geräte. Ein Ergebnis sendet der Agent bei Netzfehlern bis zu dreimal, die Installation selbst wird nie wiederholt. Dienst und `once` laufen nie gleichzeitig (systemweiter Mutex).
- **Benutzer:** Rollen Admin und Betrachter, Passwörter mit dem PasswordHasher von ASP.NET Core Identity (PBKDF2). Erster Admin aus der Umgebungsvariable `OMNIKIT_ADMIN_PASSWORD`. Cookie nur über HTTPS, `SameSite=Strict`.
- **HTTPS:** Caddy davor (eigenes Zertifikat für das LAN oder Let's Encrypt für eine Domain). Der Agent lehnt `http://` ab; für Caddys LAN-Zertifikat kann beim Registrieren dessen Stammzertifikat mitgegeben werden. Dann gilt **nur** dieses (Pinning, seit 11.11.2026): Auch Stellen, denen Windows vertraut (z. B. von Virenscannern oder einer SSL-Prüfung im Firmennetz), werden abgelehnt, weil der Agent als SYSTEM auf Zuruf des Servers Programme installiert. Zwischenzertifikate (Caddy: Stamm → Zwischen → Server) nimmt der Agent aus dem, was der Server mitschickt; geprüft werden außerdem Name, Gültigkeit und der Zweck „TLS-Server“. Umleitungen folgt der Agent nicht.
- **Angaben des Proxys (10.11.2026):** Dass eine Anfrage über HTTPS kam und von welcher Adresse, erfährt der Server von Caddy (`X-Forwarded-Proto`, `X-Forwarded-For`). Diese Angaben gelten nur mit `Server__TrustProxy=true` (in `docker-compose.yml` gesetzt, dort ist der Server von außen nicht erreichbar). Ohne die Einstellung werden sie ignoriert – sonst könnte jeder, der den Server direkt erreicht, „HTTPS“ vortäuschen und die Anmeldebremse umgehen.
- **Schutz-Angaben für den Browser:** Der Server setzt sie selbst (`Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`), damit sie auch ohne Caddy gelten; Caddy ergänzt nur `Strict-Transport-Security`.
- **Audit-Log:** jede Änderung (Anmeldung, Code erstellt, Gerät registriert/entfernt, Aufgabe angelegt/freigegeben/abgelehnt/Ergebnis, Benutzer, Gruppen).

**winget als SYSTEM:** Der Dienst startet winget aus dem Installationsordner des App-Installers (`C:\Program Files\WindowsApps\Microsoft.DesktopAppInstaller_…_x64__8wekyb3d8bbwe`), weil es für SYSTEM keinen `WindowsApps`-Aufruf im Benutzerprofil gibt. Ohne Benutzersitzung fehlt winget dort die Visual-C++-Laufzeit (Fehler `0xC0000135`, „DLL nicht gefunden“); deshalb kommt der Ordner `Microsoft.VCLibs.140.00.UWPDesktop_…_x64__8wekyb3d8bbwe` vorne in den Suchpfad (am 02.11.2026 auf der VM geprüft: ohne → 0xC0000135, mit → läuft). Beide Ordner gehören Windows (TrustedInstaller), dort kann niemand DLLs unterschieben.

**Grenzen:** Als SYSTEM sieht winget nur Programme, die für alle Benutzer installiert sind (auf der VM 3 statt 11); Programme, die es nur „pro Benutzer“ gibt, lassen sich nicht für einen bestimmten Benutzer installieren. Die Programmliste auf dem Server ist deshalb die Sicht „für den ganzen PC“.

**Installation des Agents:** `register` und `install` legen alles unter `C:\Program Files\Omnikit Agent` ab (nur Administratoren dürfen dort schreiben; der Unterordner `config` mit dem Token nur SYSTEM und Administratoren). Der Dienst läuft immer von dort, nie aus z. B. „Downloads“, damit niemand die .exe eines SYSTEM-Dienstes austauschen kann.
